# Decisions made while building all modules into the demo

You were not available, so I chose the simplest reasonable option each time something was open. Every choice is listed here with the reason. Tell me which ones you want changed.

Brief: `MarketMind Lab demo all modules prompt.md`. Session start: Thu 19 Nov 2026, 15:50 CET. This file grows with every module, and it is committed together with that module.

## Before the first module

1. **I build on the published state.** My commits sit on top of the published commit `19be820`, so a normal `git push` will publish them when you decide to.
2. **Nothing is pushed or deployed.** Both repositories are committed after every module, as the brief asks.
3. **No independent reviews,** as the brief asks.

## How the nine modules fit into the demo

4. **The runs of the new modules are "weekly exercises".** The assignment in the story covers segmentation, positioning and conjoint analysis. The new modules work with the company data of the same case, so their runs appear in the same run history, dated in October and early November, before the assignment. They are there from the start of the demo. Only the three conjoint runs still appear when you press "Run 2 scenarios".
5. **One results screen per module, built by hand, and one setup screen for all of them.** The results screen follows the pattern of the conjoint results: run header, then numbered layers (Headline, Key results, What if, Details, Interpretation). The setup screen is one generic screen that reads the engine's description of each setting. It shows the steps of the module and the inputs from `MODULES.md`, and every setting with the engine's own "what it does" and "when to choose" texts, also for every option of a choice. It is view-only, like the segmentation setup. Reason: the brief asks for the engine's texts, and one generic screen guarantees that no text is retyped.
6. **"Watch out" is the pattern for a teaching trap.** A white card with an amber edge and a tag "Watch out": one plain sentence as the title, a short explanation, then the evidence (a chart or a table). Where the engine has its own warning for the case, it is quoted word for word under "The engine says".
7. **The trap numbers come from runs on the case data, not from the validation on 50 data sets.** Example: the validation says that the Bass model was usable in 6 of 50 cases with 4 quarters. The demo shows what happens on the Alpine Oat data itself: with 4 quarters the engine finds no market potential, and the forecast is 678% too high. Reason: the brief says every number must come from the export, and a run on the case is what a student would see.
8. **The AI tutor sits at the end of each results screen,** as a layer "Interpretation". It opens with the same mode plate as the tutor panel (Coach mode, "set by Prof. Marti for the weekly exercises"). The student's own reading comes first, as a text box with a scripted note. Then one coach question, one student reply (a click inserts it, as in the tutor panel) and one closing question. No hints here, to keep the exchange short. "Write interpretation" in the run header scrolls to it.
9. **The module is called "Forecasting",** not "Bass forecasting" as in the concept, because the engine's module also covers smoothing for existing products.
10. **The professor's module list shows every module that is built.** Only the three modules of the assignment are ticked. The sentence about modules "in development" counts down by itself.
11. **The filter of the run history becomes a list to pick from** as soon as there are more than four modules. Chips for twelve modules would fill five lines.

## Engine: the export

12. **The new modules are exported by a new file,** `marketmind/export_demo_modules.py`, called from `export_demo.py`. The existing part of the file is unchanged, so the existing screens read exactly what they read before. The new part is under `modules`, and the engine's description of the settings under `settings_help`.
13. **Numbers of the new modules are rounded to nine significant digits,** not to six decimals. Reason: the browser repeats some calculations and must match the engine within 0.1%. Six decimals are too few for a small number such as p = 0.0000931.
14. **The export also holds the engine's texts:** the description of every setting, and the `warnings` and `how_to_read` of each result. The demo shows them word for word. All other sentences stay in the demo.
15. **Three small sums are done in the export, not in the demo,** so that the demo only formats numbers: the 95% range of an estimate (the estimate plus and minus 1.96 standard errors), the forecast added up over the next 12 months, and the sales of the 12 months before.

## Demo: shared building blocks

16. **The new line charts are plain SVG** (`src/components/plot.tsx`), not Recharts. Reason: full control over the style of the concept (quiet grid, values in ink, one tooltip for the whole app), and they stay sharp at any window width. The existing charts are untouched. Bars with labels still use the existing bar component.
17. **Hovering a line chart shows one tooltip for the whole period** (a hairline plus all values of that quarter or month), so the pointer never has to hit a thin line. Every chart also has a table in "Details".
18. **Colours.** No new colours for the interface. In the new charts, data the company recorded is ink, the engine's estimate is slate, and anything that is "yours" (your what-if values, the best method, the best price) is the primary colour. The three segment colours stay reserved for the three segments. Two later modules need more: I checked a four-colour set for the network communities and a red and green pair for sentiment with the palette validator (colour-blind separation and contrast) before building anything. They are noted with those modules.
19. **Sliders are the browser's own range control** in the primary colour. The concept has no slider. The native control works with the keyboard and needs no extra code.
20. **Code layout.** One data file per module (`src/data/forecasting.ts`), one file per calculation in the browser (`src/lib/forecasting.ts`) with its check against the engine next to it, and `src/lib/checks.ts` as the list of everything `npm run check` compares. `src/data/library.ts` brings all modules and runs together.

## Module 1: Forecasting

21. **Two screens with a switch:** "New product" (the Bass model, run FC-01) and "Existing product" (four methods compared, runs FC-02 to FC-04, one per sales series). The coach exchange is on the first.
22. **Four real runs.** FC-01: `fit_bass` on the 12 quarters of the Home subscription, all settings at their defaults. FC-02 to FC-04: `compare_forecast_methods` on Original 1 L, Vanilla 1 L and Chocolate 250 ml, defaults, 12 months kept aside. The switch at the top of the second screen changes the series, and with it the run.
23. **What the browser calculates:** the Bass curve for any p, q and m (three sliders), its peak and its total. `npm run check` compares it with the engine on 16 curves: the estimate, the six what-if cases of the engine (p, q and m each 20% up and down), the four estimates from the first quarters, and the five analogies. The smoothing methods are not recalculated in the browser.
24. **Analogies.** The list "Start from" holds the engine's five example products. Their p and q are per year, and the data is per quarter, so they are divided by 4, as the engine does with `periods_per_year`. The engine's own note says that the values are illustrations. It is printed under the chart.
25. **The first trap: an early forecast.** A chart with the four forecasts (from 4, 6, 8 and 12 quarters) against what really happened, and a table: market potential, forecast for the end of 2025, and how far off it was (+678%, −22%, +7%). The forecast from 4 quarters leaves the chart on purpose.
26. **The second trap: a narrow win.** On two of the three sales series the best method is ahead by less than 3%. A table across the three runs says so, with the engine's sentence on luck.
27. **Smoothing weights of zero (open question 11) are explained, not hidden.** For Original 1 L the best weights are all 0. The screen says in one sentence that this is a result, not an error, and what it means for the forecast. The example series was not changed.
28. **A line chart of sales does not start at zero** on the second screen. Monthly sales move between 120 and 180, and from zero the differences between the methods would be invisible. Bars always start at zero.

## Module 2: Price optimization

29. **Two screens with a switch,** as in forecasting: "Price tests" (runs PR-01 to PR-03, one per product) and "From the conjoint study" (run PR-04). The coach exchange is on the first.
30. **The demo opens with Vanilla Protein 1 L,** not with the first product of the data. Reason: it is the product of the student's conjoint design, and its data show the trap most clearly. The other two products follow in the order of the data.
31. **A run reads the best price from the form that fits best.** The engine fits all three forms (`compare_demand_curves`) and the run takes the best-fitting one for `optimize_price`, as the engine's README example does. `MODULES.md` calls the straight line "the safe start": on two of the three products it is within a few centimes of the best-fitting form, and the screen shows both. The unit cost is the one of the case. No price limits.
32. **The trap: which curve to trust.** For each form the export also holds what its best price would earn if the best-fitting curve is right (`predict_demand` on that curve). On Vanilla Protein 1 L the two forms that fit equally well are 9 centimes and 0.7% of profit apart. The third fits worse, recommends CHF 1.90 and would give away 28% of the profit. The engine's two warnings are quoted under the table.
33. **What the browser calculates:** units, profit and elasticity at any price for the three forms, and the price with the highest profit for any unit cost (a formula for the straight line and for constant elasticity, a search by halving for the logit curve, as in the engine). `npm run check` compares 41 prices per form and product, the best price at the unit cost of the case and at two other unit costs (30 centimes lower and higher), and the elasticities.
34. **The what-if view has three controls:** the form of the curve (with the engine's own two sentences under it), the unit cost and "your price". Price limits are not offered as sliders. They are in the setup screen as settings.
35. **The curve from the conjoint study uses the demo's own conjoint run** (CJ-02, by segment) and the design saved in CJ-03, not the ratings-based estimate of the engine's README example. So its three points are exactly the shares the market simulator shows (59%, 45%, 33%), and `npm run check` confirms that. Market size (50,000 litres per week) and unit cost (CHF 1.20) are the ones of the case.
36. **The two sources disagree, and the screen says so.** The store tests put the best price at CHF 2.47, the conjoint study at CHF 3.16. I did not smooth this over: it is what the two data sets of the case give. The card names what each source measures. One sentence of `MODULES.md` ("real demand reacts less sharply" than a conjoint curve) does not hold for this case, where the stores react more sharply than the survey (elasticity −3.3 against −1.0 to −1.3). I left that sentence out of the screen. You may want to look at it in `MODULES.md`.
37. **"Write interpretation" on a second screen of a module** (existing product, from the conjoint study) leads to the module's first screen and scrolls to its tutor, not to the interpretation of the assignment.
38. **The three demand curves are not labelled inside the chart.** Inside the tested prices they lie on top of each other, so labels would collide. The legend names them, the tooltip gives all three values at every tested price, and the table below shows where they differ.

## Module 3: Predictive modeling

39. **One screen, two models.** A switch at the top changes between logistic regression (TG-01) and the decision tree (TG-02). Both are real runs of `compare_response_models` on the 5,000 customers of last year's campaign, with the engine's defaults: 30% kept aside for testing, seed 2026, threshold 0.5, ten groups, tree depth 4.
40. **The models are not recalculated in the browser.** The brief names them as "not simple". What the browser calculates is the campaign: profit by the share of the list that gets a letter, for any cost per contact, margin per response and list size. That is simple arithmetic on the engine's ten groups. `npm run check` compares it with `campaign_profit` for both models and five sets of numbers each.
41. **The list size is 50,000.** The engine measures the profit on the 1,500 test customers and can scale it to a list (`n_customers`). The case does not name the size of this year's list. I took 50,000, the number of the engine's own README example, and the setup screen says that it is the list this exercise plans for. Cost per letter (CHF 2.50) and margin per subscriber (CHF 30) are the ones of the case.
42. **The trap: the hit rate.** The card shows the hit rate next to the hit rate of guessing "nobody responds" (86.0% against 85.7%), and a table that the export makes for it: the same model at the thresholds 0.5, 0.3, 0.2 and 0.1. The more responders the model finds, the lower its hit rate. The engine's own sentence is quoted below, and for the tree also its warning that it predicts "no" for everyone.
43. **No tree diagram.** `MODULES.md` suggests one. The tree has 29 nodes, and a readable drawing of it is a screen of its own. The details list its 15 final groups as rules instead, each with its size and response rate, with the variable names replaced by the labels of the case.
44. **"No clear effect" in the weights table** marks a weight that chance alone would produce in more than 5% of cases. Age and region are the two predictors planted without any effect, and they are the ones marked. The note under the table says that about one predictor in twenty looks clear by chance (`MODULES.md`).
45. **Scoring new customers (step 7 of the module) is not shown.** The setup screen names it as "not part of this run".

## Module 4: Customer lifetime value

46. **One screen, two runs.** LV-01 is the main run: the retention rate of each segment from the cohort data (`estimate_retention`), then the value of the 3,882 current subscribers per segment (`lifetime_value_by_segment`), with the engine's defaults (margin earned at the start of each year, the whole relationship counted), the discount rate of the case (8%) and the acquisition costs of the case. LV-02 is the same calculation with the one retention rate of all subscribers. It exists to show the trap, and the two can be compared in the run history.
47. **The three segments keep their colours and shapes.** The subscribers belong to the three segments of the survey, so this is the one new module that uses the segment colours. The export puts them in the order of the other screens (Health-focused, Taste-driven, Price-sensitive).
48. **Two traps in one card.** The engine found both: a new Price-sensitive subscriber is worth CHF 143 and costs CHF 160 to win, and with one retention rate for everyone the same subscriber seems worth CHF 201 while the customer equity comes out 24% lower. The card shows the two runs side by side and quotes both warnings of the engine. The retention chart shows the reason: the line of all subscribers rises with age, the lines of the segments do not.
49. **What the browser calculates:** the lifetime value formula with the engine's three conventions, the value each of the first ten years adds, the running total, and the year in which the acquisition cost is paid back. `npm run check` compares it with the engine for the average new subscriber of each segment and for four other customers, each with all three conventions (21 cases).
50. **The what-if view opens on the Price-sensitive subscriber,** because that is where a slider changes the answer: at a retention rate of about 60% the value passes the acquisition cost.
51. **The cohort table is a heat map in the details,** as `MODULES.md` suggests: intakes down, ages across, darker where more subscribers are left. It shows the shares of all segments together. The numbers are counted from the cohort file in the export.
52. **The 95% range of a retention rate** in the details is the rate plus and minus 1.96 standard errors of the engine. This small sum is done in the demo, as an exception to point 15, because the engine reports the rate and its standard error side by side.

## Module 5: Resource allocation

53. **One screen, two runs.** RA-01 is `allocate_budget` on the four regions with the budget of the case (1,000 thousand CHF) and the engine's defaults: the whole budget is spent. RA-02 answers step 6 of the module ("is the budget itself right?"): a budget of 1,500 with the rule "spend up to the budget". The engine spends 1,132 of it and leaves the rest.
54. **Amounts stay in thousand CHF per year in the tables,** as in the data, and the screen says so. Running text and the headline numbers are written out in francs (CHF 424,000), rounded to the thousand.
55. **The search for the best split is not repeated in the browser.** The engine needs a search in two stages for it, because simpler searches get stuck. What the browser calculates is the value of a split the student chooses: sales, profit and "what one more franc earns" for each region, from the engine's curves. `npm run check` compares the four curves at 41 spendings each, and eight whole splits (today's, the best one, four others, and the two runs).
56. **The trap: the judgments.** The export runs the best split eight more times, each time with one answer of one manager 2% lower or higher (the third answer: sales with 50% more advertising). Bern's best budget moves between 143 and 240. `MODULES.md` asks to "let students change one judgment and see the split move". In the demo this is a table of real runs, not a slider, because of point 55.
57. **"Basel gets nothing" is shown as a result, not as an error,** with the two profits that explain it (830 with today's advertising, 958 with none). In my trials Basel stayed at zero, or within 1 of it, when its first or last answer was changed by 5 to 10%.
58. **"Is the budget itself right?" is a chart of 34 real runs:** the best split for 17 budgets from 400 to 2,000, each with both budget rules.
59. **The response curves are small charts side by side,** one per region, each on its own scale, with the manager's answers as points. The curve of the Romandie is drawn a little further than the engine's default (three times today's spending), so that its best budget is on the chart. The extra stretch is calculated in the browser with the checked formula.
60. **The sliders of "What if" do not hold the total at the budget.** The student may overspend. The screen then says by how much, and it says when a region is outside its limits, as the engine does.

## Module 6: GE McKinsey matrix

61. **One screen, two runs.** GE-01 is `ge_matrix` on the ratings of the ten managers, with the weights of the case and the engine's defaults (scale from 1 to 5, grid cut into three equal parts). GE-02 is `ge_sensitivity` with its defaults: 1,000 sets of weights, each weight up to 20% higher or lower, seed 2026. The screen shows GE-01. GE-02 gives the crosses on the matrix, the column "Keeps its cell" and the card "Watch out".
62. **Both axes run from low to high, so "Invest and grow" is at the top right.** Many textbooks draw business strength from high to low, with the invest corner at the top left. `MODULES.md` only says "business strength across, market attractiveness up". I drew the axes like every other chart of the demo. This is open question 23 in `engine/PROGRESS.md`.
63. **The three zones are three strengths of the interface colour, not green, yellow and red.** The zones are ordered, so one colour in three strengths fits them. The style guide keeps green and red for good and bad states, and a traffic light would read as a verdict, while the matrix only sorts the units. Every zone is also named in the grid, in the key and in the table.
64. **The table next to the matrix is grouped by zone,** with the engine's sentence on what each zone means. "Hold and select" holds no unit in this case, and the table says so.
65. **The trap: a unit on a border.** Home subscription lies 0.01 points above the border between medium and high attractiveness. The card shows what the engine found: it keeps its cell in 64% of the 1,000 sets of weights, and one weight that is 6% lower moves it. The export adds one more thing for it: the matrix again without each one of the ten managers. Without M03 or M07 the unit lies in "Hold and select". `MODULES.md` asks for exactly this: "Near a border the cell depends on who rated."
66. **What the browser calculates:** the weighted average of the mean ratings for any weights, and from it the cell and the zone. `npm run check` compares the matrix with the weights of the case, each of the 20 runs with one weight changed (the new weight and the units that change their cell), four whole other sets of weights that the engine placed for this purpose, and, for every unit, that its score lies exactly on a border after the engine's "smallest change of one weight".
67. **The sliders set weights in whole points, and the screen shows what each factor then counts, in percent.** The engine scales the weights of an axis so that they add up to 100%. So raising one slider lowers the percent of the others on that axis. The last factor of an axis that still counts cannot be set to zero.
68. **The browser cuts the grid at exact thirds of the scale.** It does not read the two cuts from the file, which rounds numbers to nine digits. A score can lie exactly on a border, and it then counts as the higher level: without manager M05 the market attractiveness of Home subscription is exactly 3.6667.
69. **Scores are always rounded half up when written** (2.755 becomes 2.76). So a number from the engine and the same number added up in the browser are written the same way. In the what-if view a score within 0.005 of a border gets a third decimal, so that "3.665 medium" is not read as 3.67.
70. **"What each factor adds" is a stacked bar per unit and axis in the details,** as `MODULES.md` suggests. Its five parts are five steps of the neutral data colour, in the order of the key above them, each with a tooltip. The segment colours stay reserved for the three segments.
